# 讲解策划与设计稿

用于范围较大、关系复杂或需要多次修改的任务。设计稿记录可检查的决定和简短理由，不要求暴露完整思考过程。简单任务将相同要点压缩在上下文中。

## 从材料到讲解目标

先补完：“给谁，在什么地方看，读后能回答什么？”答案须能用图片检验，例如“看懂任一审核失败后，哪些步骤要重做”。“介绍审批”只说明题目，不能指导取舍。

内容按作用分类，再选择主结构：

|作用|问题|画面位置|
|---|---|---|
|动作/状态|谁做了什么，对象怎样变化|执行节点或对象状态|
|条件|什么情况下走这条路|所属分支旁|
|全程原则|哪些要求同时约束多个步骤|覆盖范围清楚的说明带、边界或邻近批注|
|证据/限制|凭什么这样说，什么条件下成立|贴近对应主张，不作为下一步|
|输出目标|希望获得什么，是否保证发生|明确“目标”或有依据的结果节点|

不要按原文“一、二、三”自动产生执行序列。多个原则可以并列；同一材料中的实际问答循环可以单独画主线。没有动作链时也可用关系结构回答问题。

## 信息分配

分清：必需内容、帮助理解的解释、可去掉的重复。必需内容包括用户指定项，以及支撑当前主线成立的条件、否定、异常和限制。

- 主图承担答案与必要路径；解释贴近相关节点。
- 可压缩解释，不得在压缩中提高结论确定性。
- 选择聚焦范围时明确本图覆盖什么；不能把用户要求的完整流程改成局部流程。
- 配套说明可保存完整出处和补充细节；不能把决定图中路径含义的内容藏在图外。
- 书籍总览先确定跨章主张及关系，再处理篇幅，不能将章节名排成流程。

## 三层设计稿

复杂任务建议保存在任务目录的`design.md`，复用同一个文件更新，不为每一层建独立表单。可替换字段名与表达形式，但保留可核验的对应关系。

```text
讲解目标：读者/场景/应能回答的问题
范围：已读与未读；必须保留；允许压缩；未解决疑点

内容关系：
  节点或主张ID｜准确文字｜作用｜来源
  起点→终点｜关系类型｜条件｜来源
  原则/限制｜覆盖哪些节点或区域

构图：
  比例与展示场景；阅读入口与终点（非流程图为导航）
  区域｜承载的节点/主张ID｜主次与相对空间｜最长标签
  关键连接的通道；局部展开与主线的对应
  最易误解处与解决办法；候选布局取舍（需要时）

表现：
  字形层级；颜色职责；线型；背景；插图程度
  采用的局部范例及适用理由；已查看/实际传入的参考图

验收：
  必需文字、关系、范围与硬约束
  图片/版本/最终提示词；逐项结论及证据
```

修改以这份稿为依据。与当前原图不一致时先标记差异，不能默认稿子比原图新。

## 构图草案怎样算可检查

用区域表或文字框图让人能回答：信息在哪、先读哪里、怎样跨区、难点在哪里。只写“简约、左中右、清晰箭头”不够。

例如，假设材料明确“双审核并行，任一失败返回补充，重新提交后双审核均重做”，草案可以是：

```text
主区：提交 → [主管审核 / 财务审核，并行] → 全部通过 → 发布
回路：任一审核失败 → 补充 → 重新提交 → 双审核入口
位置：审核区居中且面积最大；回路走下方独立通道。
```

这只是该虚构规则的设计示意。若原材料未定义失败处理或重审范围，保留缺口，不从范例补业务规则。

容量预检用最长真实标签和最密的区域推演，检查说明有没有承载空间、回路有没有通道。草案可以辅助发现明显冲突，但不能替代成图尺寸和可读性验收。内部示意不使用最终生图额度；若制作程序草图，也只作为规划材料，不替代生成式成品。

## 何时展示给用户

用户已给出完整范围与结构：用一两句说明选择，直接制作。

两种讲解目标会产生不同答案、必需内容放不下或资料冲突：展示最小取舍，再问一个决定结果的问题。审美探索可以内部比较，不能为了“专业流程”强制每个任务生成三版和逐步审批。
