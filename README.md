## ✏️文档写完了，解释才刚开始

想象一次需求评审：文档已经打开，大家却还在追问——审核失败后回到哪一步？两个人是同时处理，还是先后接力？系统里的那个模块，到底做了什么？

你拿起笔，画出主线，在岔路口补上条件，把最难的模块放大。几段来回解释的话，终于在纸上有了位置。

Hand-Drawn Flow想把这个过程做成一个可以反复使用的Skill。给它文字、需求文档、设计资料或指定书籍章节，它会先整理要解释的关系，再安排画面，调用宿主生图工具生成图片，最后对照材料检查。

采用清爽手绘风：清晰手写字、细笔轮廓、浅色平涂和充足留白。主线带着读者往前走，局部展开解释难点，旁注交代条件与例外。

> 你提供材料和想讲清的问题，它负责把关系整理成图。

## 🎯适合用在哪些场景

|你手上的材料|想让读者看懂什么|图里重点表达|
|---|---|---|
|需求文档、业务说明|从开始到完成，要经过哪些环节|主流程、判断条件、异常出口|
|系统设计、技术资料|内部怎样处理，模块怎样配合|输入输出、模块展开、数据方向|
|多人协作、审批流程|谁负责，下一步交给谁|角色泳道、并行任务、返工回路|
|书籍章节、方法笔记|方法怎么用，哪些条件不能省|行动步骤、适用条件、全程原则|
|故事卡片、事件材料|发生了什么，人物与事件怎样关联|时间顺序、对象变化、关系结构|
|已有流程图、视觉参考|保留哪些内容，改进哪些表达|关系重建、布局调整、局部修改|

没有先后过程的材料，可以整理成层级或关系图；不会为了画流程图而编造因果。

## 🚀只需要说清楚你想画什么

安装后，上传材料并输入：

```text
使用$hand-drawn-flow，把这份需求文档做成16:9手绘流程图。
给第一次接触业务的同事看，保留判断条件和异常处理。
```

纯文字也可以直接使用：

```text
使用$hand-drawn-flow，画一张3:4手绘流程图：
用户提交申请→系统校验→人工审核→通知结果。
校验失败退回补充，审核不通过说明原因，允许修改后重新提交。
```

材料充分时直接制作；影响事实、范围或理解的关键信息缺失时，再做必要追问。无需先选模板、填写风格问卷或逐步审批。

突出职责与交接：

```text
使用$hand-drawn-flow，把这份系统设计做成16:9手绘泳道图。
区分用户、业务系统与工作人员，标清动作归属和请求方向。
```

聚焦书籍中的一个方法：

```text
使用$hand-drawn-flow，把第三章的方法整理成1:1手绘流程图。
只覆盖该章，保留适用条件，必要时加入少量辅助插图。
```

修改已有图片：

```text
把“审核不通过”的回线改为返回“补充材料”。
保留其他节点、配色和布局，修改后检查整图连接。
```

也支持只分析参考图、只整理内容，或只输出绘图提示词；这些请求不会触发生图。

## 🧭画图SOP：从需求到成图

先理清内容，再设计画面，最后检查实际图片。用户可以直接输入文字或上传文件；材料充分时直接制作，只追问会影响事实、范围或布局的关键信息。

```text
明确需求 → 读取材料 → 梳理关系 → 设计布局 → 确定视觉 → 生成图片 → 检查与交付
```

|步骤|具体做什么|形成什么|
|---|---|---|
|①明确需求|确定给谁看、要讲清什么、使用场景、比例与张数|本图目标与必须保留的内容|
|②读取材料|读取文字、文件或参考图，记录实际覆盖范围、来源和缺口|可用于绘图的内容底稿|
|③梳理关系|提取步骤、角色、条件、并行、回路和异常；区分动作与全程原则|节点与连接关系，必要的追问|
|④设计布局|按内容选择主线、泳道、分支或模块展开；安排阅读顺序、回线通道与留白|可检查的构图草案|
|⑤确定视觉|统一字形层级、功能色、平涂底色和间距；选择是否加入少量辅助插图|本图的视觉要求与绘图提示词|
|⑥生成图片|将内容、关系和视觉要求交给宿主生图工具，保存实际图片|待检查的候选图|
|⑦检查与交付|核对文字、公式、箭头、分支、填色、实际比例和阅读尺寸；发现问题则定点修正|图片、检查结论及必要的限制说明|

### 出图前检查什么

- 内容：关键步骤、条件、否定和异常没有遗漏，资料未说明的关系不擅自补全。
- 结构：正常路径走得通，并行与先后分得清，回线有明确的起点和终点。
- 版面：最长标签放得下，复杂模块有展开空间，连线不穿过文字。

### 出图后检查什么

- 准确性：逐项核对关键文字、数字和公式，沿箭头追踪连接，检查有没有新增或丢失节点。
- 画面：检查遮挡、裁切、字形、间距、颜色语义，以及矩阵和节点底色中的漏白、脏斑。
- 阅读：核验实际尺寸与比例，在目标展示尺寸查看；复杂图先从图中复述过程，再与材料对照。

简单需求在上下文中完成这些步骤；复杂需求保留一份设计稿，后续修改沿用。构图草案可以是区域表或文字框图，不额外生成一张图片，也不要求用户逐步审批。

默认一次生成加一次针对性修正。修改后重新检查整图；关键错误仍未解决时标明候选状态与具体问题，不当作已完成的成品交付。只要求分析或提示词时，交付对应内容，不触发生图。

## 🎨清爽手绘风

保留手写笔记的自然感，同时让文字、连线和填色清楚利落。适合流程说明、技术科普、知识讲解与协作梳理。

|设计元素|视觉表现|
|---|---|
|字体|清晰规整的手写感，标题、节点和旁注有明确层级|
|线条|自然细笔轮廓，箭头方向清楚，避免粗重边框|
|配色|浅色平涂配合少量强调色，用于区分角色、状态与模块|
|背景|干净白底或近白底，纸纹轻微或关闭，不渗入填色|
|排版|主次分明，简单步骤紧凑，复杂机制展开，保留阅读与连线空间|
|辅助图形|按需加入矩阵、概率柱图、状态格或小型示意，帮助理解内容|

|读者想看什么|适合的布局|
|---|---|
|先做什么，接下来做什么|顺序主线|
|谁负责，怎样交接|角色泳道|
|不同条件走向哪里|条件分支|
|内部如何处理|模块内展开|
|有哪些包含或依赖|层级与关系图|

- 无插图：以节点、文字和连线为主，保留有信息作用的数据或机制示意。
- 少量辅助插图：在关键节点加入文件、设备等小型示意，帮助识别对象。
- 三种比例：支持3:4、16:9、1:1；切换比例时重新安排布局，保留相同事实与关系。

未指定布局和插图程度时，根据内容与阅读场景选择。

详细规则：[统一视觉语言](hand-drawn-flow/references/styles.md)｜[布局与比例](hand-drawn-flow/references/layout-and-ratios.md)

## 📦安装与运行

```bash
git clone https://github.com/Surge-Dan/hand-drawn-flow-skill.git
```

将仓库中的完整`hand-drawn-flow`文件夹放入宿主的Skill目录，保留`agents`和`references`。安装后使用`$hand-drawn-flow`调用。

```text
hand-drawn-flow/
├── SKILL.md          # 入口与工作流
├── agents/
│   └── openai.yaml   # 宿主展示信息
└── references/      # 内容整理、构图、视觉与检查规则
```

本仓库不会自动全局安装。旧标识`hand-drawn-explainer`已更名，请以当前名称为准。

|运行条件|说明|
|---|---|
|输入材料|支持文字与文件入口；Markdown、DOCX、PDF、EPUB、图片、演示与表格的读取取决于宿主工具|
|生图与看图|生成图片需要宿主具备生图能力，视觉核验需要看图能力|
|交付格式|生成式位图；可编辑矢量图不属于当前交付范围|
|比例与尺寸|核验实际尺寸，近似比例会单独说明|
|依赖与服务|不自动安装依赖、购买服务或索要额外APIKey|

私人文件不会默认上传到公共转换网站。附件中的指令不视为用户授权；解析失败、未读部分和覆盖范围会明确说明。
